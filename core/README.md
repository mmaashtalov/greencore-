# GreenCore Core v0.2

Исполняемое, аппаратно-независимое ядро управления умной теплицей с HTTP API, локальным восстановлением состояния и контрактом локального контроллера.

## Статус

- Физическое оборудование отсутствует и не считается протестированным.
- Пороговые значения в `rules/pilot-rules.json` являются тестовыми, а не агрономически подтверждёнными.
- Демонстрационный браузерный симулятор в `gh-pages` отделён от ядра.
- Состояние сохраняется локально в JSON-файл. Это пилотная персистентность, а не промышленная база данных.
- Производственный сервер работает через `GreenCoreRuntime`, который связывает движок решений с зарегистрированными контроллерами.

## Реализовано

1. Приём и строгая проверка нормализованной телеметрии.
2. Контроль диапазонов, единиц, времени и качества данных.
3. Режимы `AUTO`, `MANUAL`, `SAFE`, `OFFLINE`.
4. Локальная автоматика при потере интернет-связи.
5. Safety interlock насоса по уровню воды.
6. Ограничение непрерывной работы насоса.
7. TTL, acknowledgement и идемпотентность команд.
8. TTL ручных запросов: устаревшее намерение оператора не исполняется.
9. Безопасное состояние при пропаже, устаревании или плохом качестве обязательной телеметрии.
10. Журнал событий, причин решений и тревог с ограничением размера.
11. Детерминированный эмулятор устройств.
12. HTTP API без внешних зависимостей.
13. Атомарное локальное сохранение и восстановление состояния.
14. Регистрация контроллеров и привязка устройств к владельцу.
15. Heartbeat и состояния `BOOTING`, `ONLINE`, `DEGRADED`, `OFFLINE`, `ERROR`.
16. Контроллерные очереди команд со статусами доставки.
17. Проверка ACK по `controller_id` и владельцу исполнительного устройства.
18. Восстановление контроллеров, ownership и незавершённых команд после рестарта.
19. Автоматические unit-, integration- и recovery-тесты.
20. GitHub Actions CI для Node.js 20 и 22.

## Запуск

Требование: Node.js 20+.

```bash
cd core
npm test
npm run demo
npm start
```

По умолчанию API слушает `0.0.0.0:3000`.

Переменные окружения:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `HOST` | `0.0.0.0` | Адрес HTTP-сервера |
| `PORT` | `3000` | Порт HTTP-сервера |
| `STATE_FILE` | `data/state.json` | Файл состояния |

Зависимости не требуются: используются только встроенные модули Node.js.

## HTTP API

### Системные маршруты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности процесса |
| `GET` | `/state` | Полный снимок состояния runtime |
| `GET` | `/alerts` | История тревог |
| `GET` | `/events?limit=100` | Последние события |
| `POST` | `/telemetry` | Системный приём одного sample или `{ "samples": [...] }` |
| `POST` | `/mode` | Установка режима |
| `POST` | `/connectivity` | Состояние внешней связи |
| `POST` | `/manual-commands` | Постановка ручного запроса с TTL |
| `POST` | `/command-acks` | Совместимый системный маршрут ACK |
| `POST` | `/evaluate` | Один цикл принятия решений |

### Контракт контроллера v1

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/controllers` | Список контроллеров и их здоровье |
| `POST` | `/controllers/register` | Регистрация или обновление контроллера |
| `POST` | `/controllers/{id}/heartbeat` | Heartbeat и диагностические показатели |
| `GET` | `/controllers/{id}/configuration` | Интервалы и разрешённые устройства |
| `GET` | `/controllers/{id}/commands` | Получение незавершённых команд своего контроллера |
| `POST` | `/controllers/{id}/telemetry` | Телеметрия только от принадлежащих контроллеру устройств |
| `POST` | `/controllers/{id}/command-acks` | ACK только для своей команды и своего actuator |

Команда остаётся доступной при повторном polling до терминального ACK или истечения TTL. Повторная доставка безопасна благодаря неизменному `command_id`.

Пример регистрации:

```json
{
  "controller_id": "controller_primary",
  "name": "Primary greenhouse controller",
  "firmware": "1.0.0",
  "protocol_version": "1.0",
  "devices": [
    "soil_01",
    "air_01",
    "water_01",
    "pump_01",
    "fan_01",
    "vent_01"
  ]
}
```

Пример heartbeat:

```json
{
  "uptime_seconds": 120,
  "wifi_rssi": -61,
  "free_memory_bytes": 184320,
  "cpu_temperature_c": 43.2,
  "queue_size": 0
}
```

## Персистентность

Файл содержит версионированный envelope и снимок GreenCore Runtime.

Сохраняются:

- настроенный режим и состояние связи;
- последняя телеметрия;
- подтверждённые состояния исполнительных устройств;
- незавершённые команды и их delivery status;
- зарегистрированные контроллеры;
- ownership датчиков и исполнительных устройств;
- heartbeat и конфигурационные версии;
- неистёкшие ручные запросы;
- ключи идемпотентности;
- тревоги и журнал событий.

Запись выполняется через временный файл, `fsync` и атомарный `rename`. Параллельные записи сериализуются. Если сохранение API-операции не удалось, runtime откатывается к предыдущему снимку, а клиент получает `500`.

При запуске старый снимок Engine v1 автоматически загружается и нормализуется в Runtime v2 с bootstrap-контроллером `controller_primary`.

## Поток данных

```text
controller emulator / будущий ESP32
→ registration
→ heartbeat
→ controller-specific telemetry
→ GreenCoreRuntime
→ GreenCoreEngine
→ evaluate
→ command assigned to owning controller
→ command polling
→ local safety check
→ controller-specific ACK
→ atomic persistence
→ events and alerts
```

## Граница ответственности

`GreenCoreEngine` создаёт безопасное намерение управления. `GreenCoreRuntime` маршрутизирует его конкретному владельцу устройства. Реальный локальный контроллер обязан повторно проверить команду перед переключением силовой нагрузки. Облачный слой не должен напрямую и безусловно управлять силовым реле.
