# GreenCore Core v0.1

Исполняемое, аппаратно-независимое ядро управления умной теплицей с HTTP API и локальным восстановлением состояния.

## Статус

- Физическое оборудование отсутствует и не считается протестированным.
- Пороговые значения в `rules/pilot-rules.json` являются тестовыми, а не агрономически подтверждёнными.
- Демонстрационный браузерный симулятор в `gh-pages` отделён от ядра.
- Состояние сохраняется локально в JSON-файл. Это пилотная персистентность, а не промышленная база данных.

## Реализовано

1. Приём и строгая проверка нормализованной телеметрии.
2. Контроль диапазонов, единиц, времени и качества данных.
3. Режимы `AUTO`, `MANUAL`, `SAFE`, `OFFLINE`.
4. Локальная автоматика при потере интернет-связи.
5. Safety interlock насоса по уровню воды.
6. Ограничение непрерывной работы насоса.
7. TTL, acknowledgement и идемпотентность команд.
8. TTL ручных запросов: устаревшее намерение оператора не исполняется.
9. Безопасное состояние при пропаже, устаревании или плохом качестве обязательной телеметрии.
10. Журнал событий, причин решений и тревог с ограничением размера.
11. Детерминированный эмулятор устройств.
12. HTTP API без внешних зависимостей.
13. Атомарное локальное сохранение и восстановление состояния.
14. Автоматические unit-, integration- и recovery-тесты.
15. GitHub Actions CI для Node.js 20 и 22.

## Запуск

Требование: Node.js 20+.

```bash
cd core
npm test
npm run demo
npm start
```

По умолчанию API слушает `0.0.0.0:3000`.

Переменные окружения:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `HOST` | `0.0.0.0` | Адрес HTTP-сервера |
| `PORT` | `3000` | Порт HTTP-сервера |
| `STATE_FILE` | `data/state.json` | Файл состояния |

Зависимости не требуются: используются только встроенные модули Node.js.

## HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности процесса |
| `GET` | `/state` | Полный снимок состояния ядра |
| `GET` | `/alerts` | История тревог |
| `GET` | `/events?limit=100` | Последние события |
| `POST` | `/telemetry` | Один sample или `{ "samples": [...] }` |
| `POST` | `/mode` | Установка режима |
| `POST` | `/connectivity` | Состояние внешней связи |
| `POST` | `/manual-commands` | Постановка ручного запроса с TTL |
| `POST` | `/command-acks` | Подтверждение исполнения команды |
| `POST` | `/evaluate` | Один цикл принятия решений |

Пример телеметрии:

```json
{
  "device_id": "soil_01",
  "metric": "soil_moisture",
  "value": 41.7,
  "unit": "%",
  "timestamp": "2026-07-28T10:00:00+03:00",
  "quality": "GOOD"
}
```

## Персистентность

Файл содержит версионированный envelope и снимок GreenCore Engine.

Сохраняются:

- настроенный режим и состояние связи;
- последняя телеметрия;
- подтверждённые состояния исполнительных устройств;
- незавершённые команды;
- неистёкшие ручные запросы;
- ключи идемпотентности;
- тревоги и журнал событий.

Запись выполняется через временный файл, `fsync` и атомарный `rename`. Параллельные записи сериализуются. Если сохранение API-операции не удалось, состояние движка откатывается к предыдущему снимку, а клиент получает `500`.

При запуске:

1. файл читается и проверяется;
2. состояние проходит повторную доменную валидацию;
3. просроченные команды и ручные запросы отбрасываются с тревогой;
4. повреждённый файл переименовывается в `*.corrupt-*`;
5. система стартует в безопасном исходном состоянии.

## Поток данных

```text
device emulator / будущий контроллер
→ POST /telemetry
→ validation
→ GreenCoreEngine
→ POST /evaluate
→ команда с TTL и idempotency key
→ локальная проверка устройства
→ POST /command-acks
→ атомарное сохранение
→ журнал и тревоги
```

## Граница ответственности

`GreenCoreEngine` создаёт безопасное намерение управления. Реальный локальный контроллер обязан повторно проверить команду перед переключением силовой нагрузки. Облачный слой не должен напрямую и безусловно управлять силовым реле.
