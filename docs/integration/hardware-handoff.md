# GreenCore hardware-ready handoff

## Статус

GreenCore программно готов к замене виртуального контроллера реальным контроллером, но физические датчики, реле, насос, вентиляция и форточка ещё не подключались и не тестировались. Эмулятор не является доказательством полевой эксплуатации.

Источник истины для интеграции:

- `core/contracts/controller-contract.json` — регистрация контроллера, heartbeat, polling команд и ACK;
- `core/contracts/device-contracts.json` — телеметрия, единицы, диапазоны, качество, исполнительные устройства;
- `core/rules/pilot-rules.json` — тестовые safety-пороги; они не являются агрономической рекомендацией.

## Цепочка данных

```text
physical sensor / relay
        ↓
local controller adapter
        ↓ controller contract
GreenCore API → telemetry validation → state → policy → command
                                      ↓
                           controller polling + local interlock
                                      ↓
                                  ACK / state
```

Физический адаптер должен заменить только `ControllerEmulator`. Ядро, policy-проверки, persistence, API и Owner Console менять не требуется.

## Минимальная телеметрия

Каждый sample обязан содержать `device_id`, `metric`, `value`, `unit`, `timestamp` и `quality`.

| Метрика | Единица | Допустимый диапазон | Обязательна для AUTO |
|---|---|---:|---:|
| `air_temperature` | `°C` | −40…85 | да |
| `soil_moisture` | `%` | 0…100 | да |
| `water_level` | `%` | 0…100 | да |
| `air_humidity` | `%` | 0…100 | нет |
| `water_temperature` | `°C` | 0…60 | нет |

Допустимое качество: `GOOD`, `SUSPECT`, `BAD`, `MISSING`. Для `AUTO` обязательные показатели должны быть свежими и пригодными; иначе GreenCore переводит управление в безопасное состояние и запрещает активирующие команды.

## Минимальный жизненный цикл контроллера

1. Зарегистрировать уникальный `controller_id` и список принадлежащих ему устройств.
2. Отправлять heartbeat чаще, чем установленный timeout.
3. Публиковать телеметрию через `POST /controllers/{controller_id}/telemetry`.
4. Получать команды через `GET /controllers/{controller_id}/commands`.
5. Перед силовым переключением повторить локальные interlock.
6. Отправить `ACCEPTED`, затем терминальный `EXECUTED`, `REJECTED`, `FAILED` или `EXPIRED` через ACK endpoint.

Команда остаётся доступной до терминального ACK или истечения TTL. Повторная доставка одной команды не должна повторять физическое переключение: идентификатором идемпотентности является `command_id`.

## Обязательные локальные защиты

Локальный контроллер не должен слепо выполнять серверную команду. Минимум:

- насос `ON` запрещается при недостоверном/низком уровне воды;
- исполнительное устройство не включается при истёкшем TTL;
- неизвестное устройство, действие или владельца нужно отклонять;
- при отказе связи исполнительный слой сохраняет безопасное поведение;
- фактический результат реле подтверждается ACK, а не только отправкой HTTP-запроса.

Серверная Policy Engine и локальные interlock — два независимых защитных слоя.

## Приёмка после появления оборудования

До подключения к реальной теплице прогнать тот же набор, который сейчас проходит эмулятор:

- нормальная AUTO-работа;
- сухая почва;
- низкий уровень воды;
- высокая температура;
- `BAD`, `MISSING` и stale telemetry;
- потеря heartbeat и восстановление;
- потеря доставки команд;
- отказ исполнительного устройства;
- рестарт Core и повторная доставка ACK.

Критерий допуска: ни одна запрещённая команда не приводит к опасному силовому состоянию; разрешённая команда подтверждается физическим состоянием; журнал содержит `decision_id`, правило, evidence и ACK.

## Что остаётся вне текущего статуса

Не проверены на реальном объекте: точность выбранных датчиков, электрическая безопасность, монтаж, влагозащита, сетевое покрытие, электромагнитная совместимость и агрономическая корректность порогов. Эти вопросы решаются отдельным полевым пилотом после выбора оборудования.
