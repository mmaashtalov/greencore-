# GreenCore / «Умные теплицы!» — системные инструкции проекта

Этот файл — операционный контракт для Codex/AI-агентов и разработчиков. Он создан, чтобы не повторять ошибки подмены проекта, смешения актуальной базы с legacy-кодом и неподтверждённых заявлений о состоянии GitHub, CI или публикации.

Дата фиксации базовой точки: 2026-07-29.

## 1. Идентичность проекта и источники истины

Проект называется GreenCore; рабочее название — «Умные теплицы!». Это один и тот же проект.

Канонический репозиторий:

~~~text
https://github.com/mmaashtalov/greencore-.git
~~~

Каноническая базовая точка на дату фиксации:

~~~text
branch: main
commit: 0bfa299725a9e9925a34cf6f9573f1f22065e72b
~~~

На старте каждой задачи фактическое Git-состояние важнее имени каталога, памяти, старых сообщений и предположений. При конфликте приоритет такой:

1. текущий явный запрос Михаила определяет цель работы;
2. проверенный git remote, ref, код и тесты определяют фактическое состояние реализации;
3. README, roadmap и отчёты описывают намерения и должны сверяться с кодом;
4. старые диалоги, архивы и память — только подсказка, но не доказательство.

Нельзя считать репозиторий правильным только потому, что каталог называется greencore или содержит похожие слова.

## 2. Обязательная проверка перед любой работой

До чтения требований, поиска файлов или изменения кода выполнить и зафиксировать:

~~~bash
pwd
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short --branch
git log -1 --oneline --decorate
git ls-remote --heads origin main
~~~

Проверить одновременно:

- origin указывает именно на mmaashtalov/greencore-;
- текущая ветка и HEAD понятны;
- если задача начинается от канонической базы, HEAD соответствует проверенной точке или явно указанной рабочей ветке от неё;
- рабочее дерево и все pre-existing изменения записаны до начала патча;
- фактические каталоги соответствуют Node.js-монорепозиторию.

Если remote, ветка, commit, содержимое или рабочая директория не совпадают с ожиданием, работа останавливается на диагностике. Нельзя автоматически делать pull, checkout, reset, clean, удаление, перенос или клонирование другого проекта, чтобы «починить» несоответствие.

При недоступной сети состояние remote помечается как «не проверено», а не как подтверждённое.

## 3. Граница между актуальной базой и legacy

Актуальная база — Node.js-монорепозиторий:

~~~text
core/                         # Node.js runtime, API, persistence, policy engine
apps/demo/                    # React/Vite dashboard и Owner Console
packages/domain-model/        # общие доменные контракты
packages/simulation-core/     # автономная модель для публичной демонстрации
~~~

greencore_sprint9_v1.0.0-rc1 — старый FastAPI/Python Sprint 9. Он является только историческим legacy-архивом и не является текущей базой, источником архитектуры, требований или кода. Нельзя:

- продолжать разработку поверх Sprint 9;
- смешивать Python/FastAPI-код с текущим Node.js Core;
- переносить решения из другого GreenCore без проверки их происхождения;
- выдавать материализованный архив из Library или другого checkout за текущую ветку.

Скомпилированные .js, dist/, node_modules/, *.tsbuildinfo, временные файлы и прочий generated output не являются источником требований и не подтверждают версию исходников. Их нельзя автоматически удалять или добавлять в commit. Состояние до и после работы нужно сравнивать с исходным git status.

## 4. Роль владельца и режим работы

Михаил — владелец продукта и принимающая сторона. Он работает с телефона и не обязан иметь локальный ПК. Ассистент выполняет техническую реализацию: анализ checkout, подготовку патчей, код, тесты, сборки, документацию и подготовку артефактов.

Нельзя:

- предполагать, что Михаил может выполнить локальную команду на ПК;
- требовать «приложить файлы», если они уже должны быть восстановлены из текущего репозитория или доступного артефакта;
- утверждать, что Михаил сам выполнил техническое действие, если это не подтверждено;
- заменять отсутствие фактического доступа выдуманным результатом.

Если нужен ручной шаг во внешнем сервисе, его нужно описать отдельно как невыполненный шаг с точной инструкцией для телефона.

## 5. Цель продукта и защита от scope drift

GreenCore — аппаратно-независимая, открытая и масштабируемая IoT-платформа управления распределёнными объектами. Теплица — первый прикладной модуль, а не предел продукта.

Публичная демонстрация должна помогать стороннему наблюдателю увидеть причинную цепочку:

~~~text
телеметрия → состояние → решение → команда → ACK → измеримый результат/KPI
~~~

Модельные урожайность, прибыль, пороги и эффекты управления — демонстрационные данные, а не агрономически подтверждённые факты. Физические датчики, ESP32, реле, насосы и вентиляторы пока не считаются подключёнными или испытанными. Нельзя выдавать симуляцию за доказательство работы физической теплицы.

Любая новая функция должна отвечать хотя бы одному вопросу:

- делает ли она управление безопаснее;
- делает ли она решение объяснимее;
- делает ли она сравнение AUTO/MANUAL воспроизводимее;
- делает ли она платформу масштабируемее;
- делает ли публичную демонстрацию понятнее.

Если функция не связана с этими целями, сначала зафиксировать продуктовую необходимость, а не начинать кодирование.

## 6. Policy Engine и Decision Journal — обязательный контракт

Policy Engine — единый шлюз для команд. Обход policy-проверки запрещён.

Для каждой команды система должна:

- выполнить отдельную policy-проверку;
- принять только ALLOW или DENY;
- присвоить решению уникальный decision_id;
- сохранить сработавшее правило, причину и фактические показатели/evidence;
- связать разрешённую команду с policy decision;
- создать специализированную тревогу для запрещённой команды;
- сохранить историю решений после рестарта.

Зафиксированные политики v1:

- запрет насоса при низком уровне воды;
- запрет насоса при недостоверном датчике воды;
- cooldown перед повторным запуском насоса;
- запрет выключения вентиляции при высокой температуре;
- запрет закрытия форточки при высокой температуре;
- запрет активирующих команд при недостоверной обязательной телеметрии.

Следующий продуктовый блок после Policy Engine v1 — Decision Journal и Policy UI: владелец должен видеть человеческое объяснение того, почему система включила, выключила или запретила устройство. Журнал и UI должны использовать существующий policy decision как источник истины, а не создавать вторую параллельную логику решений.

Любое изменение policy-контракта требует тестов на ALLOW, DENY, evidence, decision_id, специализированную тревогу и восстановление истории после рестарта.

## 7. Правила реализации

- Изменения должны быть полными и типизированными там, где используется TypeScript; заглушки, фиктивные успешные ответы и «потом доделаем» запрещены.
- Сначала найти существующий источник истины и точки расширения; не создавать второй runtime, второй storage, второй policy engine или второй API без явного решения.
- Сохранять обратную совместимость persisted state и API-контрактов либо явно оформить миграцию.
- Не смешивать в одном утверждении факт, предположение и план.
- Ошибки и недоступность внешних сервисов должны обрабатываться явно.
- Секреты, токены, API keys, .env, реальные credentials и персональные данные не попадают в Git, логи, патчи или публичную демо-сборку.
- Не менять зависимости, lock-файлы, deployment-конфигурацию и инфраструктуру побочно; такое изменение должно быть отдельной осознанной частью задачи.

## 8. Минимальная валидация изменений

Команда проверки зависит от затронутого контура. Для изменений Core минимум:

~~~bash
cd core
npm test
npm run scenarios
npm run faults
~~~

Для monorepo/frontend:

~~~bash
pnpm typecheck
pnpm build
~~~

Для API, persistence, auth, policy, runtime или Docker-поведения дополнительно нужен соответствующий smoke/integration test. Для policy/persistence обязательно проверить рестарт/restore. Для публикации dashboard обязательно проверить фактический URL, загруженный JS-asset, ожидаемый маркер GREENCORE LIVE OPERATIONS и соответствие исходному SHA.

Матрица Core нацелена на Node.js 22 и 24; локальный результат на одной версии не доказывает результат другой. Требование Core по package manifest: Node.js >=22.13.0. Docker smoke-test считается выполненным только при фактическом запуске Docker.

Если инструмент недоступен, результат записывается как «не выполнено / причина», а не как PASS. «No jobs were run», skipped verify, failed deploy или HTTP 200 старой страницы не являются зелёной CI/deploy-проверкой.

## 9. Git, ветки и внешняя публикация

- Сначала сохранять исходный git status; пользовательские изменения не переписывать.
- Для разработки использовать отдельную рабочую ветку от проверенной базы, если Михаил явно не поручил работать в main.
- Не выполнять git reset --hard, git checkout --, git clean, массовое удаление, force-push, merge или удаление ветки без отдельного явного распоряжения.
- Commit, push, PR, merge, Pages/Render deployment и изменение GitHub settings не считать выполненными по намерению или локальному diff; каждый результат подтверждать фактическим remote/URL/логом.
- Автоматический merge не выполнять.
- Не клонировать и не анализировать соседние репозитории как замену текущему без явного подтверждения их remote и отношения к GreenCore.

## 10. Обязательный формат отчёта

После каждой существенной работы сообщать:

1. что изменено — точные файлы и краткая цель;
2. что проверено — точные команды и фактический результат;
3. что не проверено — причина и граница уверенности;
4. состояние Git — ветка, HEAD, dirty/untracked изменения, push/PR;
5. следующий шаг — только если он действительно следует из результата.

Использовать явные метки:

- **Факт** — подтверждён командой, кодом, тестом или ссылкой;
- **Не проверено** — доступа/инструмента/условия не было;
- **Гипотеза** — интерпретация, требующая проверки;
- **План** — намерение, ещё не выполненное.

## 11. Стоп-условия

Немедленно остановить изменение кода и сообщить Михаилу, если:

- обнаружен другой remote или другой проект;
- не подтверждены ветка/HEAD и нельзя безопасно определить базу;
- найден только legacy-архив, а актуальный Node.js checkout отсутствует;
- есть неизвестные пользовательские изменения, которые патч может затронуть;
- требуется удалить, сбросить, перенести или перезаписать файлы вне очевидного scope;
- тесты/CI/deploy дают противоречивые результаты;
- предлагаемый патч изменяет безопасность, policy, persistence или публичный API без тестового покрытия.

Правильная реакция на стоп-условие — диагностика и точный запрос направления, а не реконструкция проекта по памяти.
